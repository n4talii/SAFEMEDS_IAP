1. The hardest part of the lifecycle

For me, integration and implementation were the hardest stages. The challenge was not just writing an Express route; it was realizing that two teams could describe the same need but expect different API behavior. At times, we built an endpoint whose method or path was not the exact one the other team expected. That meant revisiting the design and restructuring the endpoint after work had already started. This took coordination as well as coding, because changing a method or response shape can affect both the producer and consumer.

One example was our Week 6 plan for `PATCH /medications/{id}/stock`. We understood the need as updating a medication's stock. During integration, the consumer's workflow showed that this was not the operation they needed; they needed to create an order. Our team then added a `POST` order endpoint. Looking back, the difficulty came from not walking through the Majiapps real use case in enough detail before implementation. We improved our communication by holding better structured meetings with partners: what action triggers the request, what path and method they expect, what data they send, and what response they need. That helped us make decisions based on the partner's workflow rather than assumptions.

The implementation side was also challenging because our application depended on multiple services. In one profile-creation issue, authentication was handled by Firebase while profile records were stored in Supabase. Understanding which service owned each responsibility took time, especially when an error appeared after a user account had been created successfully. These experiences showed me that integration is not a final step after coding; it needs to be considered when designing and implementing the feature.

2. One real cross-team issue

One cross-component issue occurred during profile creation. A new user could successfully appear as an account, but saving the profile failed with the message “Could not save your profile.” At first, I was confused because registration seemed to work, and I spent time looking at `firebase-storage.rules`. That was the wrong place to focus: Firebase was being used for authentication, while Supabase was responsible for storing the profile row in `user_profiles`. This hindered us as a team as we could not login as a Customer nor owner to see the changes we made on the UI side and how the data we pulled from Meditrac was being used

The issue became clearer after I traced the profile request through the server-side database configuration. Row Level Security was enabled on the Supabase table, but the backend client was using the public anon key. As a result, Supabase rejected the server's write under the table's policies. I corrected the server-side database configuration to use the service-role credential for this backend operation, which allowed profile creation to succeed. That credential must remain server-side and out of client code and Git, because it bypasses RLS.

This issue taught me to follow a failure through the entire request path instead of assuming that successful authentication means the database write also succeeded. I also learned to distinguish Firebase rules from Supabase RLS rather than debugging whichever configuration file I first recognized. If I faced the same issue again, I would capture the failing request, response, responsible service, fix, and resolution time in our integration log while the details were fresh.

3. What I would design differently

If I started the project again, I would verify the consumer's exact use case before choosing an endpoint path and HTTP method. For the stock endpoint, I would arrange a short partner walkthrough before implementation and agree on the operation, request fields, response shape, and error cases together. I would then update the needs document and OpenAPI contract immediately so that both teams were working from the same decision. Better structured meetings helped us later, and I would make that practice part of the process from the beginning.

I would also test a feature across its whole stack earlier: login, server configuration, database permissions, route behavior, and the consuming screen. For profile creation, an early test that registered a user and then confirmed the Supabase profile row existed would have exposed the configuration problem sooner than debugging Firebase storage rules. I would keep the partner testing and blind testing because they revealed assumptions that our own team might not notice. In the blind test, I saw another team 8 approach, including their use of DBeaver, and learned that teams can solve similar database tasks with different tools. I would keep that exchange, while writing down results and fixes more consistently.
